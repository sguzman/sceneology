# Sceneology Constitution

## 1. Domain

Sceneology owns and develops the public semantics and implementation of scenes: their constituent objects and relationships, audiovisual properties, spatial and temporal constraints, rendering, interaction, and reproducible experimentation.

The public ontology and implementations must be intelligible and usable on their own, without access to private systems.

## 2. Preserve research, including failure

Technical failures, rejected hypotheses, diagnostic material, unresolved issues, working queues and experimental versions are legitimate repository content. Describe outcomes accurately; do not silently replace failures with success stories or misrepresent provisional results.

## 3. Separate technical publication from artistic endorsement

Repository presence is **not** gallery approval. Showcase inclusion requires an explicit owner decision for the specific specimen and scope. Only `catalog/showcase.json` determines what the website displays. New items start outside the showcase.

## 4. Public-content boundary

Do not publish private discussions, copied conversation excerpts, personal venting, intimate/private context, identifying details, credentials, nonpublic source locations or unlicensed third-party material. Review the **contents** of each candidate: engineering evaluations, queues, incidents, test logs and development state are not categorically private, and can be retained after removing any private passages.

Review proposed files **before** public commits. Existing repository history must not be transplanted from private sources. Rewriting or deleting an unsafe public commit cannot guarantee it is unexposed.

## 5. Evidence and provenance

Document the actual technical status, scope, authorship, sources, licenses and limitations of each published work. Do not invent reviews, screenshots, functionality, ownership or acceptance. Public artifacts must resolve only public dependencies.

## 6. Development and authority

The project develops directly on `main` unless an explicit task-specific exception is given. Project decisions remain contestable and may be revised; the owner's choice controls the curated gallery. Membership in any external public registry requires an explicit separate decision.
